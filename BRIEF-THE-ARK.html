What survives the ship

TheArk

Six repositories · full history · somewhere else

Every register in this system answers a question about what is aboard. The plate register knows the art, the keyring knows the names, the pane watch knows the surfaces, the mirror knows the Workers.

None of them knows whether any of it will still be there next month.

This brief is about the job that answers that, why the obvious version of it is not a backup, and the two places it reads its own work back before claiming success.

I · Why the zip button is not a backup

GitHub offers a download. It produces a zip of the working tree at one moment: every file as it stands, and nothing else.

What a zip does not contain is history. No commits, no branches, no tags, no record of what a file used to be. Which sounds academic until it is not.

17 August · the Harbor
index.html — the way into the fleet — was replaced by a commit reading "Update fmt.Println message from 'Hello' to 'Goodbye'". Go. A hello-world. It sat there for twelve hours and nothing noticed, because nothing watched the panes.

It was recovered from git history. A zip taken that afternoon would have preserved the hello-world and lost the Harbor, and the archive would have looked perfectly healthy.

The whole argument for keeping this system in plain text under version control is that history is the safety net. A backup that discards the net keeps the least valuable copy of the thing.

II · Why backing GitHub up to GitHub is not a backup either

The second obvious version is a second repository. It preserves history and it is easy. It also fails to address a single one of the risks that matter.

The riskDoes a second GitHub repo help?
a bad force-pushyes
a file deleted by accidentyes — and so does git alone
a suspended accountno
a compromised credentialno
the platform itselfno

Six repositories on one account share one failure domain. A copy inside that domain is a convenience, not an ark.

THE ONLY THING THIS JOB DOES THAT THE PLATFORM DOES NOT
DO BETTER ALREADY IS PUT THE COPY SOMEWHERE ELSE.

III · What it actually does

git bundle

One file per repository containing the entire repository — every branch, every tag, every commit, the whole history. Restore is one command:

git clone amenti-live.bundle

Nothing to unpack, no special tooling, no format that needs this project to still exist in order to be read. A bundle is a git object and git will read it in twenty years.

The job clones each repository with --mirror, which takes every ref rather than just the default branch, then bundles with --all.

To R2, which is not GitHub

R2 speaks S3, so the upload is aws s3 cp against a Cloudflare endpoint. No SDK, no dependency — the ship carries no dependencies it did not write, and this is a shell command against a standard protocol.

Objects land under a dated prefix, so each run is its own snapshot rather than an overwrite:

s3://amenti-ark/2026-08-19/Amenti.live.bundle
s3://amenti-ark/2026-08-19/Fleet-Documents.bundle
s3://amenti-ark/2026-08-19/MANIFEST.txt
s3://amenti-ark/2026-08-19/SHA256SUMS.txt

Weekly, and clear of everything else

:07  the pane watch
:17  the patrol
:27  the scan
:37  the mirror
:47  the weighing

SUN 03:11   the ark
MON 00:00   the bell

Sunday at 03:11 — clear of the five strands that run every six hours, and clear of the bell. Two must never occupy one rung, and the ark is heavy enough that it should not be racing anything.

IV · The two places it reads its own work back

This is the part that matters, and it is the reason the job exists in this form rather than a simpler one.

A BACKUP THAT WAS NEVER READ BACK IS NOT A BACKUP.
IT IS A FILE WITH A HOPEFUL NAME.

Every bundle is opened

git bundle verify reads the file back and confirms it is a complete, self-contained repository. The job does not proceed on a bundle that does not verify — it names it and fails.

Without this the job would report success on a truncated file, and the discovery would happen on the one day it mattered. That is the Silent Signature with the stakes at their highest.

The verifier could not verify
git bundle verify requires a repository to verify against, and exits need a repository to verify a bundle when run from a bare directory. The first cut called it from the runner's working directory. It would have failed on all six.

Found by testing the round trip on a synthetic repository before shipping — three commits and two branches in, and git clone brought all of it back. The test that proved the mechanism also caught the bug.

And the far end is counted

An upload returning 200 is not a file that arrived. After the copy the job lists the destination and counts the bundles actually present. If the number sent and the number landed disagree, the run fails and says the ark is not off-provider.

A checksum per bundle is written alongside, so a silent corruption in transit is visible rather than inferred.

V · What it refuses

A partial ark does not pass

One repository that fails to clone or fails to verify fails the whole run. There is no partial success.

A partial backup that passes is how you discover, on the worst day, that the repository you needed was the one that quietly stopped being included.

The islands are named, not discovered

The six repositories are listed by name in the job. That is a deliberate trade: discovery would be automatic and would also silently stop covering a repository nobody removed. A hand-kept list can go stale, but it goes stale loudly — a name that is missing is a name a person can see is missing.

And it happened before the first run
Gameroom0.0. A sixth repository — 205 commits, a chess-referee Durable Object live in Cloudflare — on no list until somebody happened to look. The comment in the job warning about exactly this failure was written before the failure was discovered to have already occurred.

The first run bundled five and reported cleanly. The list was corrected and the run repeated. Six for six.

Without R2 it says so

If the R2 credentials are absent the job still bundles and still verifies, and keeps the result as a workflow artifact. That is a worse backup — same platform, expires in ninety days — and the summary states it plainly rather than letting a green run imply more than it earned.

VI · The reading, and the lamp

The job writes ARK.json and pushes it through the Glass Gate to Fleet-Documents. Four facts:

{
  "at":          "2026-08-19T21:14:26Z",
  "repos":       6,
  "failed":      0,
  "offProvider": true,
  "staleAfterDays": 8
}

The Watch reads it and shows one line. The field that matters is offProvider — a run that bundled six repositories and kept them as a GitHub artifact is not a backup against losing the account, and the difference has to be legible from outside. Otherwise the pane shows green over a copy sitting on the same platform as the thing it is copying.

LampMeans
GREENverified, and held somewhere other than GitHub
AMBERbundled and verified — and on the same platform
REDstale beyond eight days, or a repository did not bundle

Why stale is red and not amber

Every other amber on the Watch means nothing is watching — bad, and static. A backup that has silently stopped is bad and getting worse. Every day that passes widens the gap between what exists and what survives, so it gets the louder colour.

The strip is drawn independently of fleet-manifest.js, and deliberately so: whether the repositories survive is a fact that does not depend on whether a patrol made the rounds.

VII · The credentials, stated plainly

This job needs read access to every repository, including the two private ones. That makes ARK_TOKEN the broadest credential in the system, sitting in one repository's secrets.

SecretWhat it is · and how it is narrowed
ARK_TOKENfine-grained PAT. Contents: read-only, scoped to exactly six repositories. A backup job has no business being able to push.
R2_ACCOUNT_IDthe account. Not a credential.
R2_ACCESS_KEYan R2 Account API token, Object Read & Write, scoped to the ark bucket alone. It cannot reach AUDIO or SCENES.
R2_SECRET_KEY
R2_BUCKETamenti-ark
FLEET_TOKENContents: write on Fleet-Documents, so the reading can cross the gate. Already in use by four other workflows.

On expiry

The conventional advice is that a token should expire. It was rejected here, and the reason is the same one that runs through this whole brief.

This job runs weekly and unattended. On the day the token expires the job fails, and if nobody is watching Actions that week the ark simply stops. A credential that expires converts a security risk into a silent-failure risk, and this system has a long catalogue of what silent failure costs.

So: no expiry, read-only, six repositories, revocable in one click — and staleAfterDays in the reading so the Watch turns red on its own if the job ever does stop.

And one credential was found and removed
An R2 token named chess-referee build token had been active since May with Admin Read & Write on all buckets — able to delete AUDIO, SCENES, and the ark itself. It was created for a single deploy. Nothing automated used it: the repository has no workflows and the machine cannot run Node.

Deleted, with an inactive agent token beside it. One R2 credential now exists, scoped to one bucket.

IX · What it does not cover

Stated because a backup that quietly excludes something is the failure this job is built to prevent.

Not in the arkWhy · and where it lives instead
Supabasethe docket, the verdicts, the ledger, the readings. Not backed up by this job. A real gap.
R2 · AUDIOthe rendered voice archive. Re-derivable at cost, which is not the same as safe.
R2 · SCENES78 scenes no register walks. Unbacked and uncatalogued.
Worker secretsvalues live only in Cloudflare. WORKERS.json records the names so a restore knows what it needs.
Routes and triggerspartially in CONFIG.json via the mirror.

The ark restores the ship. It does not restore the voyage. Everything written in plain text under version control comes back exactly; the running state does not.

X · What it is worth

Nothing about this was urgent. No repository was at risk, no credential was known to be leaked, and git is already an excellent backup for the failures that actually happen day to day.

What changed is narrower and worth naming precisely. Until this job ran, the entire system depended on one platform continuing to hold it — six repositories, one account, one set of credentials. That dependency was invisible because nothing had ever asked the question.

The Amenti Key says a thing that exists in one place, in plain text, under version control, is a thing that survives. It had always been read per file. The ark is the first time it was read per system.
